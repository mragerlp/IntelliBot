## 3. Product definition

IntelliBot is a CAVELUX product. DXRP and LifePunch are its first proving environment, not shipped dependencies.

Product promise:

> Slap the bot in. Your existing agent connection supplies the intelligence; IntelliBot supplies the safe s&box actor, control contract, persistence, and replication.

Version 1 means:

- The customer keeps their model, provider, credentials, skills, reasoning history, and provider-side memory in their own IDE or terminal.
- IntelliBot supplies a host-authoritative Operator actor and bounded control API.
- All ordinary players see the Operator through normal s&box replication.
- Game-side memory stores compact, structured Operator episodes and summaries.
- “Learning” means persistent retrieval and accumulated structured experience—not model-weight training.
- No CAVELUX-hosted inference service is required.
- No DXRP, LifePunch, GROK, Rider, Fobiat, Chromr, or ClaudeBridge dependency appears in the reusable core.

 Package-owned session and bot registry

The runtime core must be transport-neutral.

For GROK’s development lane, an explicitly development-only adapter may expose the same narrow contract through the Facepunch native editor MCP. It must not proxy the broad editor bridge or become the production security boundary.

The external sidecar is the only model-facing MCP server in the consumer design. Prefer MCP stdio. The game initiates a loopback WebSocket connection carrying a small versioned action protocol—not tunneled MCP or unrestricted JSON-RPC.

## 6. Control and data contracts

Every mutation carries:

- protocol version
- request ID
- session ID
- opaque bot handle
- monotonic sequence
- expected state version
- expiry
- fixed action kind
- bounded typed arguments

The external API never accepts arbitrary player GUIDs, names, SteamIds, component selectors, paths, URLs, console text, or tool names. The package maps an opaque bot handle to the exact spawned pawn internally. Stale generations fail closed.

The package may record the engine GUID for diagnostics, but it must never fall back to the first controller, `Player.Local`, a name substring, or an arbitrary GUID when resolving a mutation target.

Safe version-1 actions:

- status
- spawn one Operator
- despawn
- stop
- bounded move
- bounded look
- memory list/get/upsert/delete

Explicitly excluded from version 1:

- attack or weapon use
- SuperAdmin or rank assignment
- shop, job, wallet, inventory, or economy actions
- human targeting
- arbitrary RPC
- `console_command`
- `execute_csharp`
- arbitrary `call_tool`
- editor, scene, package, asset, portal, Git, or filesystem mutation
- unrestricted batches or parallel action queues

## 7. Persistent intelligence

Use a fixed `FileSystem.Data` prefix such as:

```text
intellibot/v1/operators/<operator-id>/
├─ manifest.json
├─ profile.json
├─ state.json
├─ episodes/
│  └─ <episode-id>.json
└─ summary-current.json
```

Rules:

- Host-only writes.
- No caller-controlled paths.
- No provider credentials, prompts, transcripts, skills, raw SteamIds, player chat/audio/images, or human behavioral profiles.
- Stored text is untrusted data, never executable instructions.
- Version every schema.
- Enforce record, byte, and retention limits.
- Keep last-known-good generations and checksums because atomic replacement is not currently proven.
- Corrupt or future-version data fails safely without destructive overwrite.
- Missing memory must not prevent the Operator from spawning and stopping safely.
- Provider-side memory may complement this store but is not its canonical owner.
- Cross-machine synchronization and `FileSystem.OrganizationData` remain post-v1 decisions.
- Game persistence and IntelliBot memory are separate domains. Synthetic actors must never enter normal player persistence.

Suggested episode fields:

- EpisodeId
- OperatorId
- SessionId
- OccurredUtc
- TaskSummary
- OutcomeCode
- Lessons
- Tags
- EvidenceRefs
- SchemaVersion
